# debug-toolkit

Operating guidance for AI agents working in this repository.

## What this is

A minimal, non-root, read-only-rootfs-friendly network/HTTP debug image for Kubernetes - see [README.md](README.md) for what's in it and how it's meant to be used (thrown up ephemerally with `kubectl run`/`kubectl debug`, not deployed as a long-running pod). It exists to fill a real gap: neither [podium](https://github.com/platformfix/podium) nor [kubernetes-toolkit](https://github.com/swade1987/kubernetes-toolkit) ship HTTP load/latency tools, so the alternative was grabbing a random throwaway image off Docker Hub whenever `ab` or `httping` was needed in-cluster.

## Constraints that matter

- **`httping` is built from source in a separate compiler stage, and carries one patch - don't "simplify" either away.** Alpine doesn't package `httping` at all (checked both the stable and edge/community repos, confirmed empty). Upstream's own time-measurement function (`get_ts()` in `utils.c`) mixes a deprecated, unreliable field of `gettimeofday(2)` into every timestamp; on musl libc (this image's C library) that field isn't reliably populated, so it reads near-garbage stack values on every call. Verified directly: an unpatched build reported multi-million-millisecond and negative round-trip times against a real host; with the term removed, the same request reports sane, consistent numbers. The Dockerfile's builder stage explains this inline - if you touch the httping build, keep the patch and keep testing against a real host before trusting the output, not just `--version`.
- **The final image needs `libintl` (not `musl-libintl`), or `httping` fails to start.** `httping` links against `libintl.so.8` at runtime because of the same upstream quirk that requires `-DUSE_GETTEXT=ON` to link at all (the CMake build calls `bindtextdomain`/`textdomain` unconditionally in `main.c`, regardless of the `USE_GETTEXT` option). `musl-libintl` looks like the obvious musl-native package for this but only ships a header for build-time use, not a runtime `.so` - verified directly, installing it changed nothing and the binary still failed to load. `libintl` is the package that actually provides `libintl.so.8` (commit `ae629f6`).
- **The image runs non-root (UID 10001, no `$HOME`) under a read-only root filesystem, and has no capabilities of its own.** Don't add anything that assumes a writable rootfs, a home directory, or root - `/tmp` is the only writable path, and only because the deploying pod spec mounts an `emptyDir` there (see README). Tools that need raw sockets (`tcpdump`, `mtr`'s ICMP mode) need `NET_RAW` granted at the pod level; the image deliberately doesn't bake in `setcap` grants of its own; keep it that way rather than trying to make every tool work with zero pod-spec cooperation.
- **The weekly scheduled rebuild in `image.yml` is the freshness mechanism for `apk`-installed packages, not a version-bump-PR bot.** Unlike kubernetes-toolkit's curl-installed tools, `apk add <package>` doesn't pin an exact version - the same Dockerfile can produce a materially different image a week later purely because Alpine's own package repo moved on. Dependabot separately handles the base image's own digest (`docker` ecosystem in `.github/dependabot.yml`). If a genuine "bump this tool's pinned version" need ever shows up (e.g. `HTTPING_VERSION`), that's a different kind of automation than either of these - don't conflate them.
- **`test.yml`'s `build` job never logs into GCR, deliberately.** It builds with `push: false`, which needs no registry credentials at all - and Dependabot-triggered PR runs don't receive repository secrets by design, so a login step there would always fail for a dependency-bump PR regardless of the change being tested. This was a real bug discovered and fixed on kubernetes-toolkit; it was built correctly here from the start - keep it that way if you touch this workflow.
- **`PUBLIC_GCR_JSON_KEY` and `RELEASE_TOKEN` are GitHub Actions secrets, not files anywhere in this repo or retrievable via API - they can only be regenerated, not recovered.** Both come from the `circle-ci@swade1987.iam.gserviceaccount.com` GCP service account (confirmed via its actual IAM roles - `artifactregistry.writer`, `containerregistry.ServiceAgent`, `storage.objectCreator` - not assumed from the name), the same one kubernetes-toolkit's key comes from. If either secret is ever missing or needs rotating: `gcloud iam service-accounts keys create` for a fresh GCR key, or a PAT with `repo`+`workflow` scope for `RELEASE_TOKEN` - then `gh secret set <NAME> --repo swade1987/debug-toolkit < file`, and delete the local key file immediately after. Never assume you can read an existing secret's value back out.

## Commits and pull requests

Conventional Commits, enforced on both commit messages (`commit-lint`) and PR titles (`pr-lint`) - a squash merge takes its message from the PR title. Every commit must also carry a DCO `Signed-off-by:` trailer (`git commit -s`) and a valid cryptographic signature - both are required-status-check/ruleset rules, not just convention. Direct pushes to `main` are blocked by the branch ruleset; open a PR.
